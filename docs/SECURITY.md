# Security model

Passwords: Node crypto scrypt N=32768, r=8, p=1, 16-byte random salt and 64-byte output; timing-safe comparison. Sessions: 32-byte random bearer access/refresh secrets with SHA-256 hashes stored in DB; refresh rotates atomically with replay rejection; access lifetime 15m, session 30d. Native refresh in SecureStore; web HttpOnly, SameSite=Strict, Secure in production cookie scoped to /auth; access only in memory. Tokens must not be logged. Web Locks serialize refresh-cookie rotation across tabs where supported; existing access tokens remain valid for their bounded lifetimes. Fallback behavior without Web Locks requires additional testing.

Server guards every request using unexpired session rows. Conversation membership, author ownership, reciprocal accepted contacts, blocks, group administrator roles and consent state are checked server-side. Parameterized SQL; Zod validation; bounded bodies, messages and group sizes; helmet headers; strict origin checks; per-IP process-local rate limiting. WebSockets accept authenticated handshakes and contain no message content, with periodic credential revalidation and explicit revocation disconnects. No arbitrary plugin evaluation or external content rendering. React Native renders text, not raw message HTML.

Production config requires PostgreSQL, SMTP and HTTPS WEB_ORIGIN. Place API behind a TLS reverse proxy and bind private database/object-store ports internally. The development mailbox must never be deployed or bound to LAN; index.ts refuses non-loopback development mailbox configurations. No production bypass verification or shared demo password.

No E2EE implementation. Future work must evaluate maintained audited protocols such as Signal or MLS libraries including native/web bindings, multi-device identity verification, key backup/revocation, forward secrecy and metadata risks. Do not invent cryptography or label TLS as E2EE. Message plaintext storage must be disclosed. No security audit or penetration-test certification has occurred.

Known release gates: distributed abuse limits, email deliverability, fallback multi-tab refresh validation, large-history export bounds/streaming, file scanning/validation before uploads, full moderation/appeals, native security/storage lifecycle verification and dependency advisories in development tooling. See the actual verification report for current audit counts. Never apply `npm audit fix --force` to bypass Expo compatibility.

## X-Center ID trust boundary

The callback accepts only an unexpired attempt tied to the initiating browser, then takes it once before exchanging the authorization code. The official SDK pins issuer endpoints and validates the code exchange and subject. An existing Unmasked password and live session are required to bind a verified incumbent account. Provider email, username and roles never grant existing Unmasked ownership or authority. The reverse proxy keeps account request logs off, and the API excludes request URLs and authorization values from logs so that callback codes cannot enter them.

Delegated tokens stay within an expiring per-session memory store. Hosted settings are user-owned and private. Requests check the current Unmasked session, and use the user grant rather than any service key. Hosted conflicts preserve existing state. Friend matching is scoped to verified linked adults with discovery enabled and excludes blocks in both directions. Browser cookie routing, live consent revocation, and native device flows need staging evidence before release. See [the integration and migration plan](features/XCENTER_ID.md).
